## 2026-10-22 — Dataset storage at scale

- `datapoints` is hash-partitioned by `dataset_id` (16 partitions; migration `c5d8e2f71a04` copies the rows into the new table, renumbers positions in their existing order, and drops the old one). Primary key `(dataset_id, id)`; `(dataset_id, position)` unique; bucket index extended with `position`.
- Ingest uses psycopg COPY. `datasets.counts` holds per-bucket counts maintained on every write under a dataset row lock; list pages, dataset meta and project stats no longer count rows.
- Keyset paging: the dataset rows route and the `get_datapoints` tool accept `after` and return `next_after`; `offset` still works. Exports, cleaning, profiling and snapshots stream rows in 5,000-row batches; JSONL downloads stream on their own session.
- Every new snapshot is frozen as Parquet shards through the configured artifact backend, local or R2, and writes no `snapshot_rows`; the importer uses the same path. Legacy SQL snapshots still load.
- Alembic autogenerate ignores the partition children. Models and the migrated schema compare with no differences.
- Autosplit reads only `id`, `bucket` and `source` and applies every move in one set-based UPDATE (unnested arrays). On 200,000 rows it went from 255.7 s with per-row ORM updates to 8.1 s.
- Cleaning, autosplit and snapshot creation run inline up to `TINYSTUDIO_SYNC_ROW_LIMIT` rows (default 100,000, in `.env` and `.env.example`) and above it answer 202 with a worker task (`dataset.clean`, `dataset.split`, `snapshot.create`), because Cloudflare closes proxied requests after its 125 s read timeout. The interface shows the task drawer and refreshes when the task finishes; the tool descriptions say so.
- Near-duplicate cleaning compared every row with every kept row (quadratic). It now looks up candidates through an inverted shingle index; a new test checks it removes exactly what the all-pairs version removed. On 200,000 rows with 10% near copies it takes 3.5 s.
- Also measured: the quality profile takes 7.7 s on 200,000 rows and still runs inside the request; a 150 MiB JSONL import (105,621 rows) parses, validates and loads in 7.2 s, so the 512 MiB upload cap extrapolates to about 25 s plus the R2 download.
- Measured on 200,000 rows in the test database (local backend): COPY ingest 7.8 s, a keyset page near the end 34 ms against 592 ms for the same OFFSET page, dataset meta 25 ms, a full streamed read 8.6 s, autosplit 8.1 s, a Parquet snapshot 6.2 s, and a dedupe cleaning rewrite 14.8 s.
- Verified: 111 tests pass, 10 of them new (storage plus the near-duplicate equivalence test) (partition layout, COPY round trip, counters after every kind of write, position uniqueness, keyset coverage, single-partition plans, Parquet snapshots and sharding, composite-key bulk updates, the worker path for large datasets). A headless browser pass on a throwaway loopback instance covered sign-in, first-project creation, two JSONL uploads, an inline split and snapshot on a 12-row dataset, and a queued split and snapshot on a 30-row dataset with the limit set to 20; both tasks succeeded and the interface showed the drawer. The development database was dumped first (`~/.tinystudio/backups/`), then migrated. Live checks through the public hostname covered keyset pages, the streamed download, stats, and an R2 Parquet snapshot created, read back and deleted.
